# 📜 ADR 0001: การเลือกสถาปัตยกรรม Modular Monolith แทน Microservices

## 1. Title
**ADR 0001: การเลือกสถาปัตยกรรมแบบ Modular Monolith สำหรับแพลตฟอร์ม UP-Notes**

---

## 2. Status
**Accepted** — 25 สิงหาคม 2569

---

## 3. Context (บริบทและข้อจำกัดของโปรเจกต์)
- **ขนาดทีมและระยะเวลา:** ทีมพัฒนาประกอบด้วยสมาชิก 4 คน มีระยะเวลาในการพัฒนาและส่งมอบผลิตภัณฑ์ 8 สัปดาห์
- **สเกลผู้ใช้งานที่คาดหวัง:** ผู้ใช้งานหลักคือนิสิต มพ. มีปริมาณผู้ใช้งานพร้อมกัน (Concurrent Users) ประมาณ 150 คนในช่วงสัปดาห์ก่อนสอบ
- **ข้อจำกัดด้านการดูแลระบบ (Ops Capacity):** ไม่มีวิศวกรดูแลเซิร์ฟเวอร์เฉพาะทาง (Dedicated DevOps Engineer) ในทีม
- **ความต้องการทางธุรกิจ (Business Velocity):** ต้องสร้างโปรเจกต์ที่ทำงานได้แบบ End-to-End เพื่อนำเสนอสาธิต (Demo) ได้รวดเร็วตั้งแต่ Sprint 2

---

## 4. Decision (การตัดสินใจ)
ทีมตัดสินใจเลือกใช้สถาปัตยกรรมแบบ **Modular Monolith** โดยใช้ **Next.js 14 (App Router)** ซึ่งรวมเอาส่วนแสดงผลหน้าเว็บ (Frontend UI) และส่วนประมวลผลเซิร์ฟเวอร์ (Backend Route Handlers) อยู่ภายในคลังโค้ดเดียว (Single Codebase/Repository) 

โดยมีการแบ่งโครงสร้างภายในเป็นมอดูลอิสระชัดเจน (Modular Separation by Domain) ดังนี้:
1. `modules/auth`: ระบบสมัครสมาชิกและยืนยันสิทธิ์
2. `modules/notes`: ระบบค้นหา พรีวิว ไดน์โหลด และอัปโหลดชีทสรุป
3. `modules/admin`: ระบบจัดการรายงานปัญหาและควบคุมเนื้อหา

หากในอนาคตมีบริการใดต้องการการประมวลผลหนักเป็นพิเศษ (เช่น ระบบ AI ย่อเอกสาร PDF) จึงค่อยพิจารณาแยกบริการนั้นออกเป็น Microservice อิสระในภายหลัง

---

## 5. Consequences (ผลลัพธ์และข้อดีข้อเสีย)

### ✅ ผลลัพธ์เชิงบวก (Positive Consequences)
- **ความง่ายในการ Deploy:** มีหน่วยการปรับใช้งานเพียง 1 ยูนิต (Single Deployment Unit) ผ่าน Vercel หรือ Docker ช่วยลดเวลาการตั้งค่าเซิร์ฟเวอร์
- **ลดความซับซ้อนของการสื่อสาร:** ไม่ต้องจัดการ Network Latency, Service Discovery หรือ Distributed Tracing ระหว่าง Microservices
- **เพิ่มความเร็วในการพัฒนา:** สมาชิกในทีมสามารถสลับทำงานทั้ง Frontend และ Backend ได้สะดวกรวดเร็วโดยไม่ต้องสลับ Repository
- **ประสิทธิภาพดีพอสำหรับเป้าหมาย:** ทำงานได้รวดเร็วและเพียงพอกับปริมาณผู้ใช้งาน 150 คนพร้อมกัน

### ❌ ผลลัพธ์เชิงลบที่ต้องระวัง (Negative Consequences / Trade-offs)
- **ความเสี่ยง Tight Coupling:** หากทีมไม่มีวินัยในการแบ่งขอบเขต Module อาจเกิดปัญหาโค้ดพันกันจนแก้ไขยากในอนาคต
- **การขยายระบบ (Scaling):** ไม่สามารถแยกขยายเครื่องเฉพาะบางส่วนที่มีโหลดสูงได้ ต้องทำการ Scale ทั้งแอปพลิเคชันพร้อมกัน

---

## 6. Alternatives Considered (ทางเลือกอื่นที่ได้รับการพิจารณา)

### 1. Microservices Architecture (แยก 3–4 Microservices)
* *ข้อพิจารณา:* แยกเป็น Auth Service, Note Service, และ Admin Service อิสระ
* *เหตุผลปฏิเสธ:* เพิ่มภาระซับซ้อนในการตั้งค่า Docker Network, API Gateway, CORS และการจัดการฐานข้อมูลแบบย่อย (Database per Service) ซึ่งเกินความจำเป็นสำหรับทีมขนาด 4 คนและระยะเวลา 8 สัปดาห์

### 2. Fully Serverless Architecture (AWS Lambda / Cloud Functions)
* *ข้อพิจารณา:* เขียนเซิร์ฟเวอร์แบบกดเรียกใช้เป็นรายฟังก์ชัน
* *เหตุผลปฏิเสธ:* เกิดปัญหา Cold Start Latency ซึ่งส่งผลกระทบต่อ NFR ด้าน Response Time (≤ 1.5s) และยากต่อการทดสอบเครื่อง Local
