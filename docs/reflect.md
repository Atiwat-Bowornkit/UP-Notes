# 💭 Reflection Document (Post-quiz 3 Exit Ticket) — Lab 3

เอกสารการสะท้อนคิด (Reflection & Exit Ticket) สำหรับ **Lab 3: Requirements Documents**

---

## 1. การแปลงความต้องการจาก User Scenario มาสู่ User Story & Acceptance Criteria
* **ประเด็นการเรียนรู้:** การรับรู้ความต้องการของผู้ใช้ในรูปแบบเรื่องเล่า (Narrative Scenario) ช่วยให้ทีมเข้าใจบริบทและข้อจำกัดของผู้ใช้จริง เช่น กรณีของ Persona "Mint" ที่ต้องอ่านพรีวิวชีทสรุปบนรถขบ มพ. ผ่านมือถือ ทำให้เราค้นพบความต้องการเรื่องการทำ Responsive View และการบีบอัดไฟล์ภาพพรีวิวให้โหลดเร็ว
* **การปรับใช้:** การเปลี่ยนความต้องการเหล่านี้ให้อยู่ในรูปแบบ User Story (`As a... I want... So that...`) พร้อมกำหนด **Acceptance Criteria (Given/When/Then)** ช่วยให้ผู้พัฒนาและผู้ทดสอบมีเกณฑ์ความสำเร็จที่ชัดเจนตรงกันแบบวัดผลได้

---

## 2. การป้องกันปัญหา Feature Creep ด้วย MoSCoW และ Quality Bar
* **ประเด็นการเรียนรู้:** เมื่อเริ่มต้น Brainstorm ฟีเจอร์ มักเกิดความอยากใส่ฟีเจอร์ที่ซับซ้อน เช่น ระบบ AI สรุป PDF หรือระบบแชตระหว่างนิสิต แต่เมื่อนำมาผ่านกรอบ **MoSCoW Prioritization** และคำถาม **Quality Bar (INVEST Criteria)** ทำให้เราสามารถตัดฟีเจอร์ที่ไม่จำเป็นออกก่อน (จัดเป็น Won't Have ในเทอมนี้)
* **ข้อสรุป:** การมุ่งเน้นเฉพาะฟีเจอร์ Must Have และ Should Have ช่วยให้ทีมสามารถวางแผนสร้างผลิตภัณฑ์ขั้นต่ำที่ทำงานได้จริง (MVP) ภายในระยะเวลา Sprint ที่กำหนดได้อย่างทรงประสิทธิภาพ

---

## 3. การกำหนด NFR ที่เป็นรูปธรรมและวัดผลได้ (Measurable NFR)
* **ประเด็นการเรียนรู้:** คำว่า "ระบบต้องทำงานเร็ว" หรือ "ใช้งานง่าย" ไม่ใช่ข้อกำหนด NFR ที่ดี เพราะไม่สามารถนำไปทดสอบได้จริง ใน Lab นี้ทีมได้เปลี่ยนเป็นตัวเลขดัชนีวัดผล (Metrics) ชัดเจน เช่น `Response Time ≤ 1.5s ที่ p95` หรือ `ผู้ใช้ใหม่ทำภารกิจสำเร็จภายใน ≤ 2 นาที`
* **ประโยชน์ที่ได้รับ:** ช่วยให้ทีมซอฟต์แวร์สามารถออกแบบสถาปัตยกรรม (Architecture Design) และ Docker Environment เพื่อรองรับข้อกำหนดเชิงเทคนิคเหล่านี้ได้ตั้งแต่ระยะแรกของการพัฒนา
